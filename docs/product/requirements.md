# Requirements

Functional (FR) and non-functional (NFR) requirements for Tickbook, a **simulated** exchange and
paper-trading venue (no real money, no real orders, no external market data).

- Priority uses MoSCoW: **M**ust, **S**hould, **C**ould, **W**on't (this year).
- Status is `implemented` (code and tests merged) or `pending` (tracked in
  [../planning/backlog.md](../planning/backlog.md); the API surface may already answer 501).
- Traceability to tickets, modules and tests: [requirements-traceability.md](requirements-traceability.md).
- Units: prices and cash are integer minor units (cents); quantities are integer instrument units.

## Functional requirements

### E0 Foundation, identity and platform

| ID     | Requirement                                                                                                                               | Priority | Acceptance criteria                                                                                                                                                                                                                                                                            | Status      |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| FR-001 | A visitor can register a participant firm: organization, owner user and one paper-trading account funded with 1,000,000.00 simulated USD. | M        | `POST /api/v1/auth/register` answers `202` with a generic message for both new and already-registered emails; no session is issued; an existing email creates nothing and is audited as `organization.register_duplicate_email`; the new owner can then log in.                                | implemented |
| FR-002 | A user can log in with email and password and receive a session.                                                                          | M        | Valid credentials return `200`, an HttpOnly `SameSite=Lax` `tb_session` cookie and a readable `tb_csrf` cookie; invalid credentials return `401 INVALID_CREDENTIALS` with the same message whether or not the email exists.                                                                    | implemented |
| FR-003 | A user can log out.                                                                                                                       | M        | `POST /api/v1/auth/logout` deletes the session row, clears cookies and returns `204`; the old cookie then yields `401`.                                                                                                                                                                        | implemented |
| FR-004 | The client can fetch the current identity.                                                                                                | M        | `GET /api/v1/auth/me` returns user, organization, role, permission list and CSRF token; unauthenticated calls return `401`.                                                                                                                                                                    | implemented |
| FR-005 | Access is controlled by role: owner, trader, viewer.                                                                                      | M        | Viewers can read orders, accounts and market data but receive `403` on place/cancel; traders can place/cancel; owners have every permission.                                                                                                                                                   | implemented |
| FR-006 | Mutating requests made with a session require a CSRF token.                                                                               | M        | POST/PUT/PATCH/DELETE with a session but without a matching `x-csrf-token` header return `403 CSRF_FAILED`; login and register are exempt.                                                                                                                                                     | implemented |
| FR-007 | Login attempts are throttled against guessing and password spraying.                                                                      | M        | Each attempt is reserved synchronously before any I/O; per-email exponential backoff from the 5th failure; per-normalised-IP attempt limit (`LOGIN_RATE_LIMIT_PER_MINUTE`); per-IP cap on distinct emails per window; `429 RATE_LIMITED` with `Retry-After`; success clears the email counter. | implemented |
| FR-008 | Registration is rate-limited per client IP.                                                                                               | M        | More than `REGISTER_RATE_LIMIT_PER_HOUR` registrations from one normalised IP in an hour return `429`.                                                                                                                                                                                         | implemented |
| FR-009 | Security-relevant actions are written to an append-only audit log.                                                                        | M        | Login, failed login, logout, registration, order placed, order risk-rejected and order cancelled each write a row with organization, actor, entity, metadata and request id.                                                                                                                   | implemented |
| FR-010 | Operators can probe liveness and readiness.                                                                                               | M        | `GET /health` returns status and uptime; `GET /ready` returns `503 NOT_READY` when the database is unreachable and the instrument count otherwise.                                                                                                                                             | implemented |
| FR-011 | Endpoints of the target API that are not built answer with their tracking ticket.                                                         | M        | Every pending route returns `501 NOT_IMPLEMENTED` with `details.ticket` (e.g. `TB-401`), after authentication; order features not built (stop, iceberg, post-only, DAY/GTD) return `501` from `POST /orders`.                                                                                  | implemented |

### E1 Matching engine, orders and risk

| ID     | Requirement                                                                   | Priority | Acceptance criteria                                                                                                                                                                                                                                                                                                                                                                            | Status      |
| ------ | ----------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| FR-012 | Orders are validated against instrument rules.                                | M        | Quantity must be a positive integer multiple of the lot size and at most `maxOrderQty`; limit prices must be positive multiples of the tick size; violations are rejected with a stable reason (`price_not_tick_multiple`, `quantity_not_lot_multiple`, ...) and the API returns `422 ORDER_REJECTED`.                                                                                         | implemented |
| FR-013 | Matching follows price-time priority.                                         | M        | An incoming order trades against the best opposite price first and, within a price, against the earliest resting order (lowest sequence); verified by a differential test against a naive reference matcher.                                                                                                                                                                                   | implemented |
| FR-014 | Trades execute at the resting (maker) order's price.                          | M        | A buy limit at 110.20 crossing an ask at 100.00 trades at 100.00; no trade is ever outside the taker's limit.                                                                                                                                                                                                                                                                                  | implemented |
| FR-015 | A GTC limit order rests its unfilled remainder.                               | M        | The remainder joins the back of its price level; the order status is `new` or `partially_filled`.                                                                                                                                                                                                                                                                                              | implemented |
| FR-016 | Market orders sweep the book and never rest.                                  | M        | Market orders execute level by level; any remainder is cancelled with `market_no_liquidity`; a market order with GTC is rejected with `invalid_tif_for_market`.                                                                                                                                                                                                                                | implemented |
| FR-017 | IOC orders fill what is available and cancel the rest.                        | M        | Remainder cancelled with reason `ioc_remainder`; an IOC never appears in the book.                                                                                                                                                                                                                                                                                                             | implemented |
| FR-018 | FOK orders fill completely or not at all.                                     | M        | If liquidity at or better than the limit is short, the order is cancelled with `fok_unfillable` and the book is untouched; otherwise it fills fully.                                                                                                                                                                                                                                           | implemented |
| FR-019 | A firm can cancel its own resting orders.                                     | M        | `DELETE /api/v1/orders/{id}` returns the cancelled order; cancelling a filled/cancelled order returns `409 ORDER_NOT_OPEN`; another firm's order returns `404`.                                                                                                                                                                                                                                | implemented |
| FR-020 | Every accepted engine command is journaled before its effects become visible. | M        | Journal row (instrument, dense sequence, command JSON), order rows, trades, settlement and audit are written in one transaction; on failure the in-memory book is not changed.                                                                                                                                                                                                                 | implemented |
| FR-021 | Books are recovered from the journal at start-up.                             | M        | Boot replays each instrument's journal through the pure engine; a sequence gap aborts start-up; a reconciliation report lists any disagreement between books and open orders.                                                                                                                                                                                                                  | implemented |
| FR-022 | Orders pass pre-trade risk checks before matching.                            | M        | Inside the instrument's serialized section: `insufficient_buying_power` (cash minus open buy reservations across instruments), `insufficient_position` (no short selling), `position_limit_exceeded`, `notional_above_max`, `price_band_exceeded` (fat-finger vs last trade or reference price); failures return `422 RISK_REJECTED`, are persisted as rejected orders, and are not journaled. | implemented |
| FR-023 | Trades settle cash and positions immediately (gross, no fees yet).            | M        | Buyer cash decreases and position increases by price x quantity / quantity; seller the reverse; cash and positions cannot go negative.                                                                                                                                                                                                                                                         | implemented |
| FR-024 | A firm can list and fetch its orders.                                         | M        | `GET /orders` filters by `open`/`closed`/`all` and symbol with a limit; `GET /orders/{id}` returns `404` for other firms' orders.                                                                                                                                                                                                                                                              | implemented |
| FR-025 | Execution reports never disclose the counterparty.                            | M        | The place-order response lists trade id, price, quantity and liquidity flag only; no maker account or order ids.                                                                                                                                                                                                                                                                               | implemented |
| FR-026 | Client order ids are unique per account.                                      | S        | Reusing a `clientOrderId` returns `409 DUPLICATE_CLIENT_ORDER_ID` and leaves the book and journal unchanged.                                                                                                                                                                                                                                                                                   | implemented |
